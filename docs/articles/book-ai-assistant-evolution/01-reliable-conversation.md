# 图书 AI 助手的第一道坎，是把一句回答接稳

> 「图书 AI 助手演进」第一篇

给模型发一组 messages，开一个流式连接，再把返回的文字放进气泡。Demo 已经能动。

把它放进阅读 App，麻烦很快就来了。读者点了停止，连接还没断。网络中途失败，气泡里已经有半段正文。模型返回 HTTP 200，回答却停在一句没写完的话上。App 如果恰好被系统结束，下次打开时，那条没有完成的消息还会跟着历史一起发给模型。

这些情况都发生在“模型已经能回答问题”以后。麻烦才刚开始。它们会决定这个功能能不能真的交给读者。

开卷的本书 AI 从一段很短的调用流程开始。

```text
用户问题
  → system + history + user
  → 模型接口
  → 回复文字
  → 对话气泡
```

图画完了。后来加上的大部分代码，都在处理箭头之间那些没有画出来的事。

## 先把供应商挡在产品逻辑外面

开卷支持用户自己配置模型。OpenAI Compatible 和 Anthropic 的请求格式不同，流式事件也有差别。UI 若直接理解这些格式，设置页、对话页和错误处理很快会缠在一起。

第一版抽出了一层 `AiProvider`，上层只认三个动作。

```dart
abstract interface class AiProvider {
  Future<AiCompletionResult> complete(AiCompletionRequest request);
  Stream<AiStreamChunk> stream(AiCompletionRequest request);
  Future<List<AiModelInfo>> listModels();
}
```

短请求走 `complete`，长回答走 `stream`，模型列表单独读取。供应商自己的 HTTP 与流式格式留在实现内部。

这层抽象当时还很薄。它只能表达 system、user、assistant 三类消息，以及文本增量和结束原因。工具调用、usage 和更细的运行事件都不在里面。薄也有薄的好处，第一阶段只处理对话本身，先让读者收到一条可信的回答。

## 一本书不能原样塞进上下文

图书助手与普通聊天有个直接区别。用户问“他为什么在这里改口”，模型需要知道书名、当前章和选中的句子。代词立刻成了问题。旧对话也要带上一部分，否则“他”是谁都接不住。

整本书可能有几十万字，不能每轮都发。上下文也不能无限累积。开卷给每类材料设了独立上限。当前章最多取约 1 万字符，选区最多 4000 字符。历史最多保留 24 条，单条裁到 4000 字符，全部历史合计不超过 2.4 万字符。

裁剪从最新消息往前走。已经完成的 user 和 assistant 消息才能进入模型历史，失败、停止和仍在生成的消息全部排除。这样做会丢掉一部分很早的聊天，却能保证最近几轮完整，也不会让一次失败变成下一次回答的事实。

书名、正文和搜索材料还有另一种风险。一本电子书里完全可能出现“忽略前面的要求”之类句子。它只是作者写下的内容，模型却可能把它当成指令。开卷把这些材料放进 `untrusted_context`，system 里明确说明它们只供引用。这个边界不花哨，少了它，阅读内容就可能反过来改写助手的行为。

## 流式输出先要认清什么叫结束

流式接口会不断吐出文本片段。最容易写的 UI 是收到一段就追加一段。事情还没完。开卷对外传的是“到此刻为止的完整回答快照”。

假设模型先发“贾宝玉”，随后发“在这一回里”。服务层第一次交给 UI 的是“贾宝玉”，第二次交的是“贾宝玉在这一回里”。UI 每次替换正在生成的内容。

快照比增量多做了一点事，后面省下的麻烦不少。自动续写发生重叠时，服务层可以修好整段再交给 UI。某些暂时显示的内容需要撤回，也可以发一份新快照覆盖。这很有用。对话气泡不必知道供应商刚刚吐出了几个 token。

收到最后一个字也不代表这一轮已经正常完成。连接可能直接断掉，结束事件也可能缺席，模型还会因为输出上限停下。Provider 必须把正常结束、长度截断和异常断开分清。UI 才能决定把气泡标成完成、失败，还是继续等待下一段。

## 重试只有一个安全窗口

网络请求失败以后再试一次，听起来很稳妥。这里有条界线。

首个可见字符出现以前，请求失败可以自动重试。读者还没看到内容，App 重新发一次不会制造重复文字。开卷对 408、409、425、429、服务端 5xx、超时和网络中断做一次有限重试。

文字一旦出现在气泡里，静默重试就要停。第二次请求可能给出另一种开头，也可能重新计费。以后加入工具，重试还可能把同一个动作执行两遍。此时更稳妥的处理是保留已经生成的部分，让这一轮进入失败状态，再把重试决定交给读者。

规则很朴素。系统只在用户看不到差异时替他重试。

## HTTP 200 也可能只带回半篇回答

模型达到输出 token 上限时，网络请求仍然成功。OpenAI Compatible 会给出 `finish_reason=length`，Anthropic 对应 `stop_reason=max_tokens`。如果客户端只看 HTTP 状态，半篇回答会被当成完整结果保存。

开卷保留已经显示的正文，把它作为 assistant 历史重新交给模型，请模型从中断处接着写。续写请求不重新执行前面的书内动作，也不在 UI 里新增一条消息。读者看到的仍是同一个回答气泡。

模型偶尔会重复上一段末尾。拼接时，客户端检查两段首尾最多约 800 个字符的精确重叠，找到后删掉重复部分。单次回答预算是 4096 tokens，自动续写最多八轮。八轮是保护上限，防止一个异常模型不停要求继续。达到上限后，已生成内容仍然保留，读者会收到缩小问题范围的提示。

长度截断因此有了单独的处理路径。两者要分开。

## 对话历史里的消息也有状态

一条消息写进界面以后，有两个问题躲不过。它有没有完成，下一轮能不能相信它。

开卷给每轮生成分配稳定的 `turnId`，同一轮里的用户问题和助手回答一起经历状态变化。

```text
pending → completed
        → failed
        → cancelled
```

生成时，助手正文按节流频率保存为 pending 快照。正常结束、失败或用户停止以后，再用终态覆盖。如果 App 在生成途中被系统结束，下次打开会保留最后一份可见正文，同时把遗留的 pending 改成 cancelled。

读者还能看见那半段文字，模型不会在下一轮把它当成已经确认的回答。两份内容用途不同。一份留给读者，另一份留给未来的模型历史。

停止也需要沿着整条调用链传下去。按钮先更新界面，再取消网络和后续任务。界面不等待 transport 慢慢收尾。用户点下停止的那一刻，这一轮在产品上就已经结束了。

## 做到可靠对话，才轮到“会不会思考”

第一阶段没有 Agent，也没有复杂编排。模型收到一组消息，返回一段回答。代码已经要处理输入预算、流式终态和消息恢复，还得照顾用户点下停止后的那几百毫秒。

这些工作以后不会消失。工具调用会复用取消和历史，Agent 循环会复用终态与预算。换一个模型框架，UI 仍然需要知道哪段文字可信，哪一轮已经结束。

可靠对话做好以后，图书助手才遇到下一道问题。当前章足够解释一句话，却回答不了横跨全书的人物变化。整本书又放不进一次请求。

下一篇从这里开始。模型缺少正文时，应该怎样开口向 App 要，而且只能拿到 App 允许它看的那一部分。
